1 · What MarketImmune is

MarketImmune is a deterministic exchange-replay safety laboratory. It loads real Binance USD-M futures market data from a local parquet lake, overlays simulated autonomous-agent behaviour (spoofing, quote stuffing, momentum ignition, TWAP, inventory rebalancer, passive market maker) on top of each minute, runs both a hand-tuned rule engine and a trained ML risk head over the resulting feature stream, and renders the result in a professional cockpit that looks like a trading terminal.

It is not a live trading system. It does not place orders, does not subscribe to live websockets, and does not pretend to. Its entire purpose is to be a defensible portfolio project that demonstrates fintech-grade engineering skills using public research-grade data.

2 · The ML problem in plain English

Given a stream of (real) per-minute Binance order-flow features augmented with (simulated) agent behaviours, decide whether the flow at this moment looks like an unsafe / manipulative agent pattern. The output is a calibrated probability in [0, 1] which is mapped to one of three actions:

Probability rangeLabelRecommended control
[0.00, 0.40)ALLOWNo action.
[0.40, 0.75)ALERTRoute to active compliance queue.
[0.75, 1.00]BLOCKHalt connection for agent-id. Cancel floating orders.

Thresholds are stored on the model artifact itself (RiskDecisionPolicy), so the dashboard and the training script can never silently disagree about what "BLOCK" means.

Honesty rule

The aggregated bookDepth is not an L1 order book. The smallest available band is ±1% from mid. We label the resulting derived spread ±1% band spread everywhere it appears in the UI — never "L1 spread". If you remember nothing else from this section, remember that label.

5 · Inside the simulator engine

A replay is fully described by a small value object and produced by a builder service: 

@dataclass(frozen=True, slots=True)
class ReplayConfig:
    symbol: str = "BTCUSDT"
    scenario_name: str = "spoofing_layering"
    speed: int = 10
    limit: int = 120
    replay_date: str | None = None

@dataclass
class ReplayBuilder:
    kline_repo:   KlineRepository
    depth_repo:   DepthRepository
    rule_engine:  RuleEngine = field(default_factory=RuleEngine)
    risk_scorer:  RiskScorer | None = None

    def build(self, config: ReplayConfig) -> ReplayPlan: ...

The builder walks every kline, asks the chosen AgentScenario for its overlay, derives a quote from the nearest aggregated depth snapshot, feeds the features into both the rule engine and (if present) the ML head, and yields one immutable ReplayTick per minute. Persistence is the caller's job; the engine emits a deterministic value tree.

6 · Six design patterns, in this codebase

  • Strategy — AgentScenario (abstract base) plus six concrete subclasses. Every scenario implements the same step(idx, close_price) contract. The builder doesn't care which one it's calling.
  • Factory / Registry — ScenarioRegistry with a @register decorator. Adding a new scenario means writing one class. Nothing else changes; the cockpit dropdown rebuilds itself from ScenarioRegistry.catalog().
  • Repository — KlineRepository and DepthRepository hide all parquet I/O. The rest of the engine sees domain objects (KlineRecord, DepthSnapshot), never pyarrow.Table. Swap in a Kafka source by writing one more class.
  • Service — ReplayBuilder (engine) and SimulatorService (Django app). One concept each; injectable dependencies; no static globals.
  • Value object — frozen @dataclass(slots=True): ReplayConfig, ReplayPlan, ReplayTick, DerivedQuote, RiskPrediction, BenchmarkReport, RiskDecisionPolicy. Hashable, immutable, no aliasing bugs.
  • Dependency injection — every service constructor takes its collaborators by argument. The default-arguments use sensible defaults (ReplayBuilder.from_lake(...)), but tests override them with fakes.

Adding a new scenario — full code

@register
class IcebergSlicerScenario(AgentScenario):
    name = "iceberg_slicer"
    family = "benign"
    label = "Iceberg slicer"
    description = "Large parent order split into tiny visible child orders."

    def step(self, idx, close):
        return ScenarioOutput(
            features={
                "w1000_agentic_burst_rate_per_second": 2.0,
                "w5000_order_quantity_sum": 0.4,
                ...
            },
            side="BUY",
            order_price_offset=0.0,
            order_quantity=0.05,
            trade_quantity=0.05,
            trade_price_offset=0.0,
        )

Restart the dev server and the new option appears in the cockpit dropdown with its description visible underneath. No template edits, no migrations, no plumbing changes.

7 · The gradient-boosting risk head

The data

marketimmune.models.dataset.build_dataset() emits (X, y, names) where each row is one scenario's template feature vector perturbed with two sources of noise:

  • multiplicative lognormal noise on every feature (noise_std=0.55)
  • per-feature contamination: with probability 0.18 we sample a feature from the opposite family's template instead of our own.

The contamination is what stops the classifier from achieving a trivial PR-AUC of 1.0. With both ingredients turned on, the head has to learn multi-feature interactions, not lookups.

The model

GradientBoostingClassifier(
    n_estimators=200,
    max_depth=3,
    learning_rate=0.08,
    random_state=42,
)

The decision policy

Persisted alongside the model so the artifact is self-describing: 

@dataclass(frozen=True, slots=True)
class RiskDecisionPolicy:
    alert_threshold: float = 0.40
    block_threshold: float = 0.75

Explainability

Every call returns the top-3 contributing features (value × global feature importance). That string is included verbatim in the cockpit's audit panel: 

ML score 1.00 with top features [
    w1000_agentic_burst_rate_per_second=+3.38,
    w1000_agentic_min_interarrival_ms=+1.70,
    w60000_market_price_drift=+1.55,
]

SHAP would be more principled (we call this out in the roadmap), but the swap is a single method change in RiskScorer._top_contributions.

8 · Benchmark numbers and what they mean

0.989PR-AUC (test)
0.988ROC-AUC
0.944F1 @ 0.5
~0.96 msp99 latency

All four come from reports/risk_head_benchmark.json, produced by: 

python scripts/train_risk_head.py

A second invocation with the same --seed 42 produces byte-identical output. The Risk-Center page (/simulator/risk/) renders the JSON as KPI cards plus a feature-importance bar chart, and re-measures latency live with GET /api/risk-head/health/?samples=500.

Why we don't claim "Real Binance manipulation detection"

The labels here come from the synthetic scenario registry, not from a hand-curated dataset of real exchange enforcement actions. The benchmark proves the head distinguishes our six scenarios with the contamination level we picked. Doing real labels is a roadmap item (P1: "real-time event-time feature extractor"). If a recruiter asks "what's the limitation?" — this is the honest answer.

10 · Provenance and honesty rules

The first rule of recruiter-readable code

Never label a panel as "real" if the JS makes it up. The previous iteration of this project had a "Live L2 dynamic" DOM ladder filled with 0.2 + (i + index) % 3 * 0.15. That is the kind of detail that loses a candidate trust in 30 seconds. The current build is auditable end to end — every numeric value on the cockpit corresponds to either a row in a parquet file or a row in the simulated scenario.

Concretely, the project enforces three rules:

  1. Anything labelled with a green "Binance" badge originates from a parquet read. Verify with git grep depth_levels.
  2. Anything labelled simulated (violet) is sourced from the scenario registry. Verify with git grep ScenarioRegistry.
  3. Anything labelled "derived" (amber) is computed by a pure helper in marketimmune/simulator/pricing.py with the formula documented at the call site.

11 · Extending the system (interview question prep)

12 · Three talking points to memorize

1. The "what I built" sentence

"I built a deterministic replay of a real Binance order book on top of the published USD-M parquet lake, layered six configurable agent scenarios on top using a Strategy / Registry pattern, and ran a gradient-boosting risk head with a held-out PR-AUC of 0.989 and p99 inference latency under 1 ms. The whole data path is labelled with provenance — anything not coming from the parquet is rendered in a different colour and explicitly marked as simulated."

2. The architecture sentence

"The pure engine lives in marketimmune.simulator with no Django dependency, so the same builder can run in a Jupyter notebook or a backtest. The Django app talks to the engine through a single SimulatorService facade and persists the resulting ReplayPlan via one atomic bulk_create transaction per session."

3. The "what's next" sentence

"Next I want to replace the synthetic labels with real event-stream-derived features over a held-out scenario-family split, ship a small transformer-based MTPP head as a second scorer, and switch the cockpit from REST polling to a Django Channels websocket. The architecture is set up for those swaps — each is roughly one new file."

Generated as part of the simulator refactor that introduced marketimmune.simulator, dashboard.services, marketimmune.models.risk_head, the prepare_simulator command, the train_risk_head.py script, and the /api/risk-head/health/ endpoint.
